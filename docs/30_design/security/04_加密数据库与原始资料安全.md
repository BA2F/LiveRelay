## 加密 SQLite

首版要求 SQLite 在磁盘页面级整体保持密文。

未持有正确密钥时，不应让普通数据库工具直接看到：

- 表结构；
- 记录数量；
- 时间等结构化元数据。

MVP 已采用 Drift + `sqlite3` 提供的 SQLCipher 构建。运行时先读取 `PRAGMA cipher_version`，若未加载 SQLCipher 则拒绝打开，不允许静默降级为明文 SQLite；设置 VMK 后立即执行认证读取，以尽早拒绝错误密钥。

运行时数据库为 Vault 目录中的 `vault.sqlite`，当前 schema version 为 4。表包括：Source、EncryptedBlob、LifeCard、CardRevision、CardRelation、Credential、CredentialRevision、ReleasePolicy、LifeStateEvent 和 AuditEvent。代码包含 v1 → v4 增量迁移，并已在 Android 模拟器上验证保留已有数据。

## 原始资料 Blob

照片、文档、音频、视频落盘前使用 AES-256-GCM 加密。

磁盘只保存随机 ID 的密文 Blob；真实文件名、描述等信息放在加密数据库中。

当前 Blob v1 格式为 `LRBLB001 + 12-byte nonce + 16-byte MAC + ciphertext`，AAD 绑定 Blob ID。数据库内保存明文长度和 SHA-256，用于解密后的完整性复核。文件先写 `.tmp` 并 flush，再原子 rename 到随机 ID 路径；异常时清理临时文件。

MVP 单个 Blob 上限为 256 MB，当前实现为内存中加解密。原始资料随 `.lvault` 一并迁移和备份。

## Vault Header 与目录边界

`vault-header.json` 只保存格式、KDF 参数、盐、被 AES-256-GCM 封装的 VMK 和生物识别启用标记，不保存主密码或明文 VMK。数据库和 Blob 使用同一个随机 256-bit VMK，但采用不同格式和 AAD 边界。

## 当前限制与后续验证

- 需要固化跨版本迁移样本，而不只依赖运行时升级验证；
- 需要补充断电、磁盘满、半写入和恢复替换中断测试；
- 大文件需要流式加密，避免 256 MB 内存边界；
- 普通文件删除不保证底层闪存安全擦除，产品不能承诺物理不可恢复；
- Blob 与数据库跨文件事务目前依靠补偿清理，不是单一原子事务。
