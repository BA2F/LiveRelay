# 项目工作区使用手册

> 状态：当前有效  
> 版本：0.4
> 最后更新：2026-09-21
> 依赖文档：无


## 1. 顶层信息角色

- `docs/`：当前正式知识、设计和规则；
- `notes/`：讨论过程、研究草稿、原始记录；
- `records/`：需要长期保留“为什么”的重要决策；
- `memory/`：给 AI 快速恢复上下文的派生缓存；
- `tasks/`：人和 AI 共用的执行看板与 Task Spec；
- `handoffs/`：真实任务结束后的执行记录；
- `work/`：代码、图、数据、报告、PPT、导出物；
- `templates/`：当前真正需要复用的文档模板；
- `skills/`：已经经过真实重复工作验证的 Agent 工作流；
- `scripts/`：自动检查；
- `archive/`：历史快照、旧方案、初始化规范。

不要因为“要写报告、要做 PPT、要加一个功能”就新增顶层知识目录。

## 执行环境与同步

- Linux 工作区 `/home/tahzun/Development/Projects/LiveRelay` 是代码、文档、测试和 Git 操作的唯一写入位置；
- Mac 仅作为 SSH 控制端，不再修改 Mac 上的项目副本；
- GitHub `main` 保存已提交、可复现的项目状态。开始任务前先在 Linux 检查工作区，再以快进方式同步远端；
- 网络地址、私钥路径、口令等运维秘密不写入仓库。

## 2. 继续详细设计

```text
读取专题总览/相关正式结论/必要 ADR
→ 新会话讨论
→ 必要时 notes 留过程总结
→ 更新或新建真实设计文档
→ 若产生长期重要决策则 ADR
→ 若设计成熟到可实现，再产生模块/契约
→ 更新 memory 当前状态
```

**没有真实内容，不预建占位 Markdown。**

## 3. 增加新功能

先判断需求与边界，再更新产品/spec；只有当功能真正形成稳定独立职责时才新增模块。目录跟随稳定系统结构，不跟随每个需求点。

## 4. 开始写代码

```text
正式设计
→ 模块边界
→ 必要契约
→ Task Spec
→ work/code
→ 测试
→ Handoff
→ 回写设计/任务/memory/必要 ADR
```

## 5. 写报告和 PPT

报告/PPT 从 `docs + records + tasks + handoffs + work` 抽取当前事实，分别输出到 `work/paper/`、`work/slides/` 或 `work/exports/`。

它们是项目事实的“视图”，不是新的事实源。

## 6. 当前治理冻结

从 2026-09-06 起，除非真实设计或开发暴露明确问题，不新增 governance、Skill、模板或新的工作流层级。
