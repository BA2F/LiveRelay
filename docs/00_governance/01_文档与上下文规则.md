# 文档与上下文规则

> 状态：当前有效  
> 版本：0.3  
> 最后更新：2026-09-06  
> 依赖文档：无


## 1. 权威顺序

发生冲突时：

1. 人类当前明确指令；
2. `docs/` 中已确认/已冻结的正式结论；
3. `records/adr/` 中论证完整、已接受且未被替代的 ADR；
4. 当前 Task Spec；
5. `memory/当前项目上下文.md`；
6. `notes/`；
7. `archive/`。

`memory` 是缓存；`notes` 和 `archive` 可能包含旧方案。

## 2. 知识完整，执行压缩

产品思想、研究、安全论证、ADR 可以较丰富；模块说明、契约、Task 必须尽量短。

报告和 PPT 需要的设计理由应保存在正式知识或 ADR 中，而不是为了减少 Agent 上下文而删除。

## 3. 文件何时拆分

拆分单位不是“知识点”，而是**独立变化单元**。判断：

- Cohesion：内容是否天然属于一起？
- Change coupling：是否通常一起修改？
- Readership：是否有不同读者单独需要？
- Authority：是否需要独立版本、冻结或评审？

没有独立变化生命周期就不要单独建文件。

## 4. 渐进式披露

叶子 Agent 从最靠近任务的文档开始读，缺什么再向上追溯。

### 叶子开发任务

- 典型必读：4～6 篇；
- 复杂情况尽量 ≤8 篇；
- 项目文档上下文目标约 8～18K tokens。

### 叶子详细设计任务

- 典型必读：5～8 篇；
- 复杂情况尽量 ≤10 篇；
- 项目文档上下文目标约 12～25K tokens。

这些是诊断性软预算，不是机械硬限制。若一个很小的任务必须读十几篇无关文档，应优先检查模块边界、契约或任务拆分。

## 5. 不允许的默认行为

- 不因模型支持 256K/1M 上下文就全量读取仓库；
- 不默认读取 `notes/raw/`；
- 不为了“更保险”读取所有模块内部设计；
- 不把占位文档当作完成的设计；
- 不因为文件名存在就假设契约已经冻结。

## 6. 状态

当前正式文档优先使用：

- `草案`
- `讨论中`
- `已确认`
- `已冻结`
- `已废弃`

尚未产生内容的设计不创建文件，而不是创建“待设计”占位。
