# 旧库恢复事务与中断安全

> 状态：已完成（代码、76 项回归、Linux 原生及两端构建通过）\
> 日期：2026-10-03\
> 基线：`a86cec3`，Linux `codex/formal-foundation`\
> 范围：旧格式恢复及 Header 写入可靠性，不新增密钥方式

## 问题与目标

当前 `VaultKeyManager._writeHeader()` 先删除旧 Header，再 rename 临时文件；`AppController.restoreVault()` 能捕获正常异常并恢复 rollback，但进程被杀后没有可重放操作日志。初始化只检查当前 Header，可能将“原库已移走但新库未安装”误认为需要创建新库。

改为可恢复的本地文件事务：每个中断点至少保留一份库／Header，重新启动能够恢复原路径或进入明确的恢复状态，不自动创建空库、不删除未经认证的残留库。保持 Header／Blob／`.lvault` v1、数据库 schema v4、KDF 和已有口令语义；这是可靠性修正，不是多槽升级。

## 实施要求

1. 引入内部文件事务服务与可注入文件操作／阶段故障点。日志只记录随机 operationId、局部目录名、操作意图／提交状态和密文文件摘要；无密码、VMK、R 或个人内容。
2. 恢复先完整 staging 校验密码、清单认证和数据库可打开性，再准备替换。保留原数据直到明确提交；每个 rename 前写意图，日志写失败不继续破坏原路径。重启从意图与文件实际状态一致判定，不只相信最后阶段字段。
3. 初始化在判定 `needsSetup` 前检查本地事务。已知原库移走时恢复其路径并保持 locked；缺失／损坏日志且存在候选库时进入可理解的恢复状态，不默认新建。若无法安全自动处理，只展示受控问题并保留副本，不猜测选择“最新”目录。
4. Header 更新采用保持旧文件可恢复的替换流程，读取器维持原规范路径和 v1 格式；处理写入／flush／rename／提交失败。Linux／Android／Windows 的覆盖 rename 能力不得凭 Linux 结果推断，需要明确 adapter 与未验证状态。
5. 日志及 rollback／staging 目录只能位于资料库受控相邻目录；操作类型和目录名严格校验。拒绝绝对路径、穿越、符号链接、重名冲突、未知日志版本及超限输入，不用日志指定路径做递归删除。
6. 所有者 `.lvault` v1 导出只包含已提交运行库。事务日志和未提交 Header／rollback 副本须位于导出目录之外，或由明确 sidecar 排除规则覆盖；不能把同 VMK 的旧 Header 作为正常 payload 静默备份。当前归档会遍历库内所有文件，仅排除 `-wal`／`-shm`／`.tmp`，需针对新事务文件核对。
7. 恢复提交后，旧设备槽清理失败不得允许控制器直接生物识别解锁旧 VMK；`unlockWithBiometric()` 必须核对当前 Header 的启用状态，不能仅由 UI 隐藏入口。重启后也核对。此项不改变现有口令解锁或设备认证类型。
8. 清理失败不能把已经提交并可用的新库退回旧库；保留加密副本和可重试清理状态。启动修复与重复恢复必须幂等。锁定／失败释放控制器原有 repository 和 session key，不留多个可操作会话。

精确内部日志字段和文件操作实现可由本任务定义，不成为备份或跨 package 公共契约。断电持久性的保证按实际平台记录，进程重启通过不等同物理断电验证。

## 验收与必须测试

| 场景 | 结果 |
|---|---|
| 初次创建 Header、更新生物识别标志，任一步失败 | 旧可解锁 Header 保留；无 Header 时只在确实没有历史库的情况下显示创建 |
| staging 准备／验证失败 | 原库与原凭证可用；不关闭正常会话直到替换准备完成 |
| 原库 rename 前后、新库安装前后、打开数据库、提交、清理失败 | 新进程恢复原库或经认证完成新库，始终保留至少一份有效库 |
| 含旧库与新库的恢复，二者使用不同密码／内容 | 对恢复结果使用正确密码，内容与选择一致；旧密码不能被误当作新库成功 |
| 无现有库恢复、损坏日志、多个孤立 rollback、恶意目录／符号链接 | 不越界删除、不空库覆盖、显示实际恢复状态 |
| 导出发生在事务期间、导出后再恢复 | 只含已提交库与正常 v1 内容，没有运行日志／未提交副本 |
| 设备清理失败、直接调用解锁方法、重新启动 | 禁用状态拒绝读取旧设备 VMK；口令仍能正确解锁恢复后的库 |
| 重复启动恢复／清理、取消、文件系统权限或空间不足 | 幂等、无数据丢失，错误不泄露秘密 |

必须运行：`flutter analyze --no-pub`、`flutter test --no-pub`；在独立目录中运行 Linux 原生集成，真实 SQLCipher 和真实文件系统，使用不同密码的新旧虚构库。故障测试必须构造“新控制器／新进程看到的残留文件”，不能只覆盖同一次调用的 catch 路径。至少以子进程终止或等价原生过程验证一个关键 rename 临界区。

Android 真机与 Windows 的平台验证按可用环境执行并记录限制；本任务 Linux 通过不将两端标已验收。原生集成和平台构建顺序运行；不为文档修改无条件重建 APK。成功后写真实 Handoff，报告实际执行命令、结果、中断覆盖和未验证平台。

## 反馈与完成标准

若现有文件 API 无法保证至少一份可恢复副本，先停受影响替换操作并提出实现证据，不扩大格式或删除备用库。若 UI 必须新增大范围恢复选择流程，拆子任务，先保证不把中断状态路由成创建。

以上自动化与 Linux 原生证据完成，原有格式回归通过，文档回写后才能标完成；不能只因操作日志文件已创建而宣称恢复可靠。
