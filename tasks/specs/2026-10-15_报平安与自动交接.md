# 报平安与自动交接（摇篮）任务规格

> 状态：设计已确认（本人 2026-10-15 拍板），待实现
> 日期：2026-10-15
> 依赖：docs/30_design/security/07（信任边界与 D3 决策）、docs/30_design/security/11（.lrshare／.lridentity 格式）、docs/20_product/16（摇篮方向）、work/deploy/copyparty（现有云端）
> 入口证据：handoffs/2026-10-14_云端WebDAV部署到阿里云ECS.md

## 目标

把"报平安 → 提醒 → 宽限期 → 预先授权的交接"从产品方向落成可用功能。云端（copyparty，IP + HTTP）已部署，本机手动限定范围交接（.lrshare）与接收者身份体系已实现，缺的是报平安记录、服务端调度、触发交付三段。

## 本人已拍板的决策（2026-10-15）

1. 报平安方式：手动按钮为主；打开 App 自动算一次。
2. 通知渠道：先做邮件（短信后置）。
3. 服务端形态：Docker（ECS 上新增容器，与现有编排一致）。
4. 信任边界：接受"单投递方（摇篮服务）可按时间触发通知/投递"的边界，明确记录在案。
5. 交付方式：触发后邮件发送云端网址与账号密码，接收人自己上云端取件。
6. 参数：周期 7 天、提前 1 天提醒、宽限期 3 天；做成可调。
7. 顺序：①手机连通信道（已完成）→ ②报平安 + 提醒 → ③自动投递 + 接收者取件。

## 架构

```
手机／桌面 App ──报平安（覆盖写）──▶ 云端 <客户卷>/cradle/checkin.json
      │                                    │
      └─摇篮计划与预授权包上传──▶ cradle/plan.json + cradle/handoff/*.lrshare
                                           │
                            摇篮服务（ECS 新容器，只读客户卷 + 自己的状态目录）
                                           │
              距上次报平安 ≥6 天 ──▶ 邮件提醒本人（每天一次）
              距上次报平安 ≥10 天 ──▶ 邮件通知接收者取件（网址＋账号＋密码）
                                           │
                            接收者浏览器下载 .lrshare → LiveRelay 接收者模式打开
```

时间语义：昨天报平安 = 0 天。周期 7 天、提前 1 天提醒、宽限 3 天 → 第 6 天开始提醒本人；第 10 天触发取件通知。

## 云端目录布局（客户卷根目录）

```
liverelay-checkin.json      # 最新报平安记录（App 覆盖写，服务端只读）
liverelay-cradle-plan.json  # 摇篮计划（App 覆盖写，服务端只读）
```

（原设计为 `cradle/` 子目录；`TransferMedium` 端口不接受含 `/` 的文件名，实现改为根级前缀文件，语义不变。接收者的 `.lrshare` 包第二段再定名，同样放根级。）

服务端判断是否超期，用 checkin.json 的**文件修改时间**（服务器时钟），不用记录里的设备时间（设备时钟不可信，仅供参考与审计）。

## 数据格式（内部工程格式，未冻结对外契约）

checkin.json：

```json
{
  "kind": "liverelay-checkin",
  "version": 1,
  "checkedAt": "2026-10-15T12:34:56Z",
  "device": "手机",
  "publicIdentity": { ... },
  "signature": "<Ed25519，覆盖上述字段>"
}
```

plan.json：

```json
{
  "kind": "liverelay-cradle-plan",
  "version": 1,
  "ownerEmail": "me@example.com",
  "periodDays": 7,
  "remindBeforeDays": 1,
  "graceDays": 3,
  "recipients": [
    {
      "label": "家人",
      "email": "someone@example.com",
      "package": "liverelay-handoff-家人.lrshare",
      "cloudUrl": "http://47.121.136.8:3923/<客户>/",
      "cloudUser": "<客户>",
      "cloudPassword": "<密码>"
    }
  ]
}
```

说明：cloudPassword 按第 5 条决策明写（接收者取件用）。plan.json 与 checkin.json 在云端为明文；账号密码本来就是该卷的凭据，服务器管理员本就能读卷，不构成额外暴露。包内容（.lrshare）始终加密，服务端读不到。

## 摇篮服务行为

- 常驻循环（默认每 10 分钟一轮，可配）；扫描数据目录下各客户卷的 `cradle/`。
- 状态存在服务端自己的目录（容器卷），按客户记录：最后提醒日、已通知标记、已知 checkin 时间戳。
- 判定与动作：
  - 距 checkin 修改时间 ≥ (periodDays − remindBeforeDays) 天且未触发：每天一次提醒邮件给本人。
  - 距 checkin 修改时间 ≥ (periodDays + graceDays) 天：给每个接收者发一次取件邮件；发出后标记，不重复发（除非之后本人重新报平安再超期）。
  - checkin 变新（本人回来报平安）：清提醒与通知标记。
- 邮件：SMTP 配置放服务器端（凭据不入库）；发送失败要记录日志并在下轮重试。
- 多个 checkin（多设备）没有单独处理：覆盖写天然取最新一次。

## 信任边界（决策记录，依据安全 07）

- 服务端控制"何时通知/投递"，理论上可提前投递或提前通知；本人明确接受（安全 07：单投递方模型无法防提前投递；端到端加密防服务器阅读，不防服务器提前把可解密材料发给接收者）。
- 服务端打不开 .lrshare（HPKE 加密给接收者公钥）；明文只存在于 Owner 设备与接收者设备。
- 不引入独立释放秘密／独立批准者；产品若未来要求"投递方不能单独提前释放"，另立设计（安全 07 已写明方向）。

## 实施分期

第一段（本次实施）：
- App：报平安（手动按钮＋解锁后自动上报一次）、最近报平安时间显示、摇篮计划设置页（周期/提前/宽限/接收者邮箱）、上传 checkin.json 与 plan.json。
- 服务端：摇篮服务容器（扫描＋提醒邮件＋状态管理）＋ 部署资产（work/deploy/cradle/）。
- 验证：单测（编解码、时间计算、覆盖写）；服务器实测（造假数据把时间调快，收到提醒邮件）；真机走查。

第二段：
- App：交接页"设为摇篮预授权包"（选接收者 → 导出 .lrshare → 上传 handoff/）；取件状态显示。
- 服务端：取件邮件。
- 端到端验证：触发 → 接收者收邮件 → 浏览器下载 → 接收者模式打开包。

## 未决与后置

- 短信通道；离线队列重试（报平安上传失败时的本地待同步）；提醒文案最终稿；服务端多客户配额与防滥用；服务端对 plan 改动的即时感知（现为每轮重读）。
- 独立的发起人撤销协议（触发前本人可在 App 里关停摇篮——即删云端 plan.json 或置停用位，随第二段做）。

## 纪律

- 服务端组件与格式为内部工程格式，未冻结为跨 package 或对外契约。
- SMTP 凭据、服务器凭据不入库；测试账号密码不入库。
- 本 spec 即为"先设计后编码"的设计落点；安全 07 D3 要求的信任边界决定已由本人明确接受。
