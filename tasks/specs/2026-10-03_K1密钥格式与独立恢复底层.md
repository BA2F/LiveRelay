## 范围

明确并验证受限 Header v2 字节、独立随机恢复凭证、密码／恢复任一解封、全 Header 认证及 v1 兼容读取。新格式在独立虚构库评估，默认 App 创建仍使用 v1；不自动迁移用户库，不把含新 Header 的库导出成 `.lvault` v1。设备因素 K2、新备份／恢复界面 K3、AND／换钥 K4 后续实施。

## 工程取舍和前置验收

沿用安全草案的独立随机分支秘密 B、分支解封 VMK、恢复旁路和 VMK 派生 Header MAC；本片只接受一个密码分支和一个恢复分支，无设备／AND。使用严格 ASCII 受限 schema 的排序 JSON 字节；解码后重建相同规范字节，拒绝重复键、未知字段、浮点、非规范编码和超限输入，不宣称实现通用 JCS。

恢复秘密为 CSPRNG 32 bytes，采用固定 LRR1 Base64url 无填充与 32-bit 校验编码；不复用日常中文词表。密码分支评估 profile 为 Argon2id v19、64 MiB／3 次／1 lane／32 bytes，只接受该明确组；它尚未经过最低配置 Android 实测，标为内部 evaluation suite，生产默认 writer 不切换。v1 只接受既有 writer 的 19 MiB／2／1／32 参数，不接受外部无限制 KDF 参数。

实现规格与安全依赖见 [Header v2 工程格式](../../docs/30_design/security/08_Header_v2底层格式与恢复编码.md)。该文件是内部评估规格，安全／最弱目标设备复核未完成前不宣布公共稳定协议或正式安全验收完成。

## 所有权和检查

- core/security：恢复编码、受限规范字节、v2 codec、v1/v2 reader 分流；保留 v1 writer 和既有算法。
- application/VaultSession：恢复解封的内部会话方法，不把 VMK 或恢复秘密交给 UI／AI；未增加可见恢复按钮。
- infrastructure/backup：拒绝 v2 Header 被伪装成 v1 外层，保留旧备份路径。
- 使用独立 Python cryptography 原语生成 golden fixtures，验证密码和恢复分支、AAD 与 Header MAC 字节；另验证 RFC 原语向量。
- 错误凭证、删／换／改任一分支、跨库槽、未知格式／suite、恶意参数、重复键与非规范编码均拒绝，v1 无写入升级。
- 静态分析、完整回归、Linux 原生 SQLCipher／Blob 新格式验证，以及 Android／Linux release 构建；只使用虚构数据。
