## 这一轮做了什么

远端现在只有 `main` 一条线（`8d887b6`，v1.0.0-beta.2 之后），三个 codex 分支已合并删除。10-14 的 Windows 修复在旧分支上，`main` 里没有它，13 处文件提交仍直接 `rename`。本轮从 `origin/main` 拉新分支 `codex/windows-adaptation`，把修复原样落上去：这些文件在 10-14 的基线和当前 main 之间没有变化，代码与用例直接沿用，文档按新 main 重写。

代码侧新增 `lib/core/storage/file_commit.dart`，13 处调用点接入，目录提交拒绝覆盖已存在目标。用例侧复用 10-14 的移植：恢复事务改用 SDK 自带 `dart`、Linux 播放后端 PDF 用例按平台跳过、Windows 生产入口建库用例、WebDAV 死链超时调整。

## 与 10-14 不同的地方

这台机器的 `%APPDATA%\Roaming` 现在不加密了（`cipher` 显示 `U`），10-14 靠 EFS 触发的退化路径在本机不再被 `%APPDATA%` 沙箱覆盖。为了不留这个缺口，`file_commit_test` 增加了默认跳过的跨卷用例：把 C: 的临时文件改名到 E:，平台报 error code 17，与 EFS 场景同一个错误码；`commitFile` 与 `commitDirectory` 的退化提交实测都成功。

构建依赖 GitHub 直连的部分需要导出代理，否则 `pub get` 与 `sqlite3` native-assets 长时间无进展；该设置属环境配置，未写入仓库。

## 与设计差异

平台设计原写“文件系统负责……原子写入”。带 EFS 的 Windows 配置目录不存在原子替换，本轮改为“平台拒绝原子替换时使用可核对的退化提交”，裁判仍是调用方保留的已 flush 前序副本与安装后的核对。

## 新决策

- 提交路径统一收口在 `core/storage/file_commit.dart`，新写入点复用该入口。
- 退化提交按“rename 是否失败且 sidecar 是否仍在”判断，不问平台。
- 退化路径的自动化覆盖改用跨卷场景，不再依赖某台机器是否启用 EFS。

## 是否需要契约/ADR

不需要。模块内部实现变化，契约不变。

## 未解决与技术债

- Windows 指纹、密钥环存储、接收者身份、交接与备份恢复未验证；release 只验编译与产物。
- 未在 Linux 复跑；Linux 与普通 NTFS 仍走原子 rename。
- 退化提交期间进程被强杀可能留下半写文件；已有前序副本与安装后核对可发现，没有自动修复入口。
- 跨卷用例需要人工指定第二块磁盘，默认不跑。
