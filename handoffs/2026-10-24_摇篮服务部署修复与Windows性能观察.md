> 触发：本人上报摇篮邮件发不出，App 点「检查测试结果」没有结果

## 出了什么事

App 把测试请求上传到云端，WebDAV 返回 201，摇篮服务没有任何反应。等满一个巡检周期也没有结果文件，Windows 那台控制机因此判断摇篮服务没在运行。

## 为什么

服务一直在跑，跑的是 2026-10-17 的镜像。10-21 加的测试邮件和计划 v2 不在这个镜像里：v2 计划每 10 分钟被拒一次，日志写 `invalid plan (kind/version)`；测试请求文件根本没有代码去读。

补上新代码后，第二层问题才露出来：数据目录从 10-15 起就是只读挂载，而新代码要写结果文件、删请求文件。日志报 `[Errno 30] Read-only file system`。

`send_mail` 排在写结果前面。每轮巡检都先把邮件发出去，再在写结果时失败。请求文件删不掉，下一轮又发一遍。重复发信就是这么来的。

## 怎么处理的

1. 传仓库版 `cradle.py` 上去，`docker compose up -d --build` 重建。
2. compose 里 `/data` 的挂载从 `:ro` 改成 `:rw`。
3. 删掉 `users/test3` 里残留的测试请求，先停掉重复发送。
4. 在 `/srv/tttahzun/inventory/services.yaml` 补 `liverelay-cradle` 条目。

快照放在 `/srv/tttahzun/backups/20261024-174424-cradle-v2-update/`，里面有 `SHA256SUMS`、旧 `cradle.py`、改动前后的 compose。

## Windows 为什么慢

本人反馈 Windows 输密码解锁慢、弹文件框也慢，Linux 没这感觉。

解锁由三段组成，用户等的是三段之和：Argon2id 派生密钥、打开 SQLCipher、把整份资料库读进内存（卡片、密码条目、附件列表、策略、历史）。

本机 Linux 实测 Argon2id：冷启动 143 ms，预热后 82～86 ms。v2 头部那套 64 MiB、3 轮的参数是 455 ms。第一段是固定成本，不到 0.2 秒，撑不起「明显慢」。

`cryptography_flutter` 只给 Android、iOS、macOS 提供原生实现。Windows 和 Linux 跑的是同一份纯 Dart 代码，KDF 解释不了两边的差距。

更像的原因在第三段：快照加载和资料库大小成正比。Windows 上那个库如果记录多、附件多，解锁自然慢。本人说的「Linux 可能文件较少」正好对上。

还有一个可能：Windows 跑的是 debug 构建。debug 下 JIT 和断言会让所有 Dart 代码慢好几倍。

文件框那边，Windows 用的是 `windows_file_picker` 2.0.0，每次调用新开一个 isolate，在里面初始化 COM 再弹系统对话框。Linux 的 `file_picker_linux` 2.0.1 走 XDG Desktop Portal，D-Bus 连接和代理对象第一次用完就复用。新建 isolate 在 release 下只有几毫秒，debug 下会明显拖时间。Windows 文件对话框本身还会加载第三方 shell 扩展，第一次弹通常最慢。

## 还要确认什么

- Windows 上跑的是 release 还是 debug 构建。
- 两边的资料库记录数和附件数是不是一个量级。

确认办法：把同一份 vault 目录分别放到 Windows 和 Linux，各解锁一次并计时。Windows 再用 `flutter run --profile -d windows` 打开 DevTools 时间线，看主线程耗在哪一段。
