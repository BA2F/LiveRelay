## 代码行为

- `core/storage/recoverable_file.dart`：先 flush 前序副本与新暂存文件，再替换规范文件；规范 Header 缺失时从受限、格式可解析的前序／暂存恢复，密码解封和数据库读取仍负责真实认证。64 KiB 上限；拒绝链接与非普通状态文件。`.tmp` sidecar 不进入现有归档。
- `infrastructure/backup/vault_restore_transaction.dart`：恢复前有本地意图，安装并验证后有独立完成标记；目录名由随机操作 ID 派生，日志仅记录局部名称、阶段所需状态和 Header 密文摘要。操作记录和 incoming／rollback 在运行库外。
- 启动检查恢复记录后再决定创建／解锁。未提交且有原库时保守找回原库；没有原库时只沿该意图中已验证的 staging 恢复，随后要求备份密码。损坏记录和孤立候选保留文件，进入失败状态，不自动创建空库。
- 完成后的清理失败保留新库及加密残留；启动不会按未经认证的操作记录递归删除目录。成功流程只清理本次已核对的旧库。未知残留没有自动删除。
- 控制器检查当前 Header 是否启用指纹，再读取设备密钥；恢复后即使设备清理失败，旧槽也不能被直接解锁调用读取。密码与已启用指纹仍是独立日常入口。
- 失败会话不能通过调用 `lock()` 变成正常解锁路由。恢复提示在解锁页／成功提示展示；没有大范围 UI 重做。

涉及 `app_controller.dart`、`vault_key_manager.dart`、恢复对话框／解锁页，以及两个新内部文件。测试新增 `recoverable_header_test.dart`、`vault_restore_transaction_test.dart`、`restore_recovery_test.dart`、纯 Dart 子进程退出 worker 和 `restore_recovery_desktop_test.dart`。

## 限制、设计差异与下一步

测试过程中修正了首次恢复 staging 被误认作孤立残留的问题：新操作只豁免自己经过父目录／命名／文件校验的 staging，启动仍拒绝无记录的未知候选。修复后最终完整回归与原生集成重新通过。

生物识别单元验证使用受控存储替身，不等同真机指纹。未验证 Android／Windows 的文件替换中断、实体生物识别、物理断电或真实磁盘满。`flush` 和进程退出验证不证明各平台目录断电持久性。Android 构建仍有已有 Kotlin 迁移提示，未升级依赖；Drift debug 的多数据库实例提示来自不同测试目录／staging executor，未隐藏该诊断。

损坏／缺失日志的孤立库目前只保留并进入失败状态，尚未提供完整的候选副本人工选择界面。清理失败的加密残留会保留并提示，没有自动批量清理未认证副本。后续恢复辅助界面与跨平台故障验收单列；不要为重现故障操作真实用户库。

没有更改既有稳定格式或公共端口，不需因 K0 建立新的加密 ADR。新的恢复／密钥槽／接收者包仍参考 [安全草案](../docs/30_design/security/07_正式版密钥恢复与接收者解密设计.md)及 [实施拆分](../tasks/specs/2026-10-03_正式版密钥与交接实施拆分.md)推进：默认 OR 和独立恢复优先，可选 AND／强化换钥后置；手动交接仍需完整字段与身份协议。
