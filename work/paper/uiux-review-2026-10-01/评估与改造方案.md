# 留灯 UI/UX 评估与改造方案

> 评估日期：2026-10-01\
> 状态：方案已获用户确认，当前可实现范围已实施；见 [实施与验证交付](实施与验证交付.md)\
> 基线：`7c4f30e`，Linux main 与 origin/main 同步\
> 方法：产品文档、Flutter 表现层和相关控制器检查、Android 16 模拟器走查。未开展真实用户访谈。

## 结论

当前界面已形成一致的暖色视觉风格，也具备记录、卡片、密码和交接的基本入口。下一轮应优先让用户能轻松留下信息、可靠找回信息、看懂授权结果，再做视觉精修。

最大落差是：产品希望用户“先留下，再慢慢整理”，界面却过早要求用户理解卡片、草稿、来源、释放层级和技术术语。安全与长期可信的底层能力，需要转化为可见的保存状态、可理解的来源、可恢复的删除和可核对的交接内容。

## 1. 评估范围与证据边界

本轮实测了：创建测试资料库、四个主导航页面、创建并查看一张虚构卡片、交接策略弹窗、搜索与跨页返回、设置和解锁。使用独立 Android 用户 `LiveRelay-UX-Review`，未修改原用户资料库。

照片/OCR/AI、密码显示与复制、回收和来源访问的结论来自源码检查，未在本轮完整联调；深色模式、TalkBack、系统大字体、真实生物识别和大规模数据未验收。截图对应已安装的 MVP；未重新构建 APK，也未通过二进制校验宣称安装包与当前源码完全一致。已走查的页面文案和结构与源码对应。

本报告中的优先级是设计判断，不是事故等级；时间和成功率属于建议验收目标，不是已测出的用户数据。

## 2. 产品哲学应如何体现在体验上

| 产品原则 | 用户真正需要感受到的行为 | 当前判断 |
| --- | --- | --- |
| 生前持续使用 | 此刻记下来，下次找得到 | 高频记录入口明确，但表单和首页较重 |
| 本地优先、本人掌控 | 明白保存在哪里、何时会外发、怎样恢复 | 技术说明很多，恢复和备份状态不够突出 |
| 原始资料优先、可追溯 | 能从结论回到原件，区分录入、推断和确认 | 数据层已有基础，详情页缺少直达来源的路径 |
| AI 可选、人工确认 | 不用 AI 也能完成整理，清楚知道发送了什么 | 单次授权正确，行级 Token 操作负担偏高 |
| 明确授权、有限交接 | 能核对在某个场景下对方实际看到什么 | 目前强调生命状态模拟，授权结果解释不足 |
| 长期可信 | 更新不丢历史，删除可恢复，换设备能恢复 | 历史已展示，但回收与恢复入口未形成完整体验 |

依据：[产品定位](../../../docs/20_product/02_产品定位与价值主张.md)、[产品总览](../../../docs/20_product/00_产品设计总览.md)、[核心使用场景](../../../docs/20_product/04_核心使用场景.md)。其中使用场景及导航文档仍标为“讨论中”，不能当成冻结验收契约。

## 3. 值得保留的设计

- “留灯”、灯泡和暖色可以承载关怀、日常陪伴与个人掌控，不必重新塑造品牌。
- 四个主入口基本对应真实任务；密码库的专门入口有高频价值，设置不占主导航合理。
- 新信息默认本人可见、AI 每次授权、AI/OCR 结果先成为草稿，符合产品立场。
- 显示与复制密码分开、显示后定时遮挡、备份导出前重新验证，都有明确作用。
- 保留修订历史和“本人确认”动作，可以继续发展为可信来源的可见表达。

## 4. 主要问题与改造建议

### P0：先修复会损害信任或误导操作的体验

**A. 搜索会让首页误报“还没有记录”——已实测复现。**

步骤：创建 `Insurance-demo` → 卡片页搜索 `zzznomatch` → 返回记录页。首页“全部卡片”仍为 1，“最近记录”却变成空状态。清除搜索后卡片重新出现，数据没有被删除。

原因：卡片搜索结果写回共享的 `controller.cards`，首页也使用这份列表。建议把页面搜索结果与完整数据、首页最近数据分开；操作刷新后也应保持搜索词与实际结果一致。

证据：[搜索无结果](screenshots/search-empty.png)、[返回首页后误报空](screenshots/search-leaks-home.png)；[控制器](../../code/live_relay/lib/application/app_controller.dart) `_refreshUnlockedData`、[记录页](../../code/live_relay/lib/presentation/pages/capture_page.dart) `cards.take(5)`。

**B. 首页拍照、录像、录音按钮对比度过低——已实测观察。**

这些按钮可以操作，但深棕字叠在棕色背景上，看起来接近禁用状态。截图采样的主要前景 `#7B3700` 与背景 `#9A4D16`，对比度约 1.44:1；这是单一截图的像素估算，不代替全主题审计。

建议缩小首页品牌色大背景，把采集入口放到浅色表面，或明确为容器内按钮配置相匹配的前景色。保留暖色作为主行动强调色。

证据：[首页](screenshots/home.png)、[主题](../../code/live_relay/lib/presentation/design_system/app_theme.dart)、[采集按钮](../../code/live_relay/lib/presentation/pages/capture_page.dart)。

**C. “基本信息”不等于经过选择的摘要——源码确认。**

卡片交接预览中的“基本信息”直接取正文前 80 个字符；正文较短时直接显示全部。若用户把敏感内容写在开头，该标签可能造成错误预期。密码条目的“基本信息”则展示账号和网址，同一个等级在不同信息类型中含义不同。授权后的密码在演示视图中直接展开，和日常密码库默认遮挡的行为不一致。

短期：在策略选择时显示精确预览，明确说明当前“基本信息”的内容规则；密码仍默认遮挡，主动查看。后续如引入本人确认的交接摘要或字段级选择，需要产品和领域模型评审，不应由界面层擅自更改授权语义。

证据：[策略弹窗](screenshots/policy.png)、[handoff_page.dart](../../code/live_relay/lib/presentation/pages/handoff_page.dart) `_ReleasedCard` / `_ReleasedCredential`。

**D. 删除和恢复入口未形成完整路径——界面与源码确认。**

详情提供“移入回收区（保留历史）”，但当前主界面没有找到回收区列表和恢复动作；代码查询会排除已删除条目。新建资料库和解锁页面也没有“从备份恢复”，恢复只能从已解锁后的设置进入。

建议补齐“回收区 → 查看 → 恢复”，删除后提供撤销；把“从加密备份恢复”放入首次使用及解锁页。恢复前展示备份时间、数据范围和替换影响。真正需要永久清除时再单独确认。相关能力涉及应用层与仓储，不能只换按钮文案。

证据：[详情](screenshots/detail.png)、[首次使用](screenshots/setup.png)、[设置](screenshots/settings.png)；[card_dialogs.dart](../../code/live_relay/lib/presentation/dialogs/card_dialogs.dart)、[gate_page.dart](../../code/live_relay/lib/presentation/pages/gate_page.dart)、[仓储](../../code/live_relay/lib/infrastructure/persistence/sqlite_vault_repository.dart)。

### P1：把日常任务做顺

**E. 快速记录过早变成卡片整理——已实测。**

点击“新建记录”后，依次出现标题、内容、类别、标签和草稿开关。类别和标签虽然不必主动填写，仍然占据注意力。默认保存为“已确认”，只写“保存”的按钮没有把这个结果说清楚。完整的本人输入可直接成为正式卡片符合当前产品方向；问题是快捷入口没有区分“先存着”和“我已确认”。

建议：快捷记录以内容为起点，标题可由首行提取，类别与标签收进“补充信息”。主要动作叫“先保存”，明确进入待整理；另提供“确认保存”为本人确认内容。离开未保存编辑时提供保留或放弃选择，保留必须使用现有加密边界。

证据：[编辑页](screenshots/editor.png)、[card_dialogs.dart](../../code/live_relay/lib/presentation/dialogs/card_dialogs.dart)。

**F. 首页展示入口和统计，却没有把“下一步”组织好——已实测。**

首页七个采集按钮，加上重复的新建悬浮按钮和三个统计块，使最近内容在首屏底部才开始出现。统计卡没有跳转动作，“待确认”数量不能直接带用户处理内容。长期使用后，固定大横幅仍然占据同样空间。

建议：把主行动收敛为“记一条”，配拍照、录音、更多；导入与录像进入更多。首页依次显示快捷记录、可点击的待整理入口、最近记录。空库展示一条具体示例，如“备用钥匙放在哪里”，已有内容后缩小引导。

**G. 原件保存与长期找回之间存在入口缺口——源码确认。**

记录页只展示 `blobs.take(4)`，没有“全部原件”入口；卡片详情也没有可点击的来源/原件区域。媒体查看器侧重回放，没有把“原件 → 识别文本 → 草稿”连接为可持续操作的整理流程。原件是否存在于存储和用户是否能再次找到，是两个问题。

建议：增加全部原件列表及搜索/类型筛选；卡片详情提供原件、来源片段、确认时间和修订入口。手机整理界面采用“查看原件 / 整理内容”两个可切换视图，保留上下文。音视频没有自动转写时，仍能手工添加关联说明。

**H. 查找入口按系统状态分类，较少照顾用户记忆方式——已实测与源码确认。**

卡片页先出现“待确认、已确认、已拆分”，人物关系仍是普通卡片类别，没有独立的人物列表/详情体验。新用户还没搜索就收到“没有匹配的卡片”。

建议：保留“卡片”作为当前名称，先增加人物、位置、资产等类型筛选；“已拆分”移入历史/高级筛选。区分空资料库、搜索无结果、筛选无结果、加载失败。可以用后续用户测试决定是否把卡片页改名为“资料”，不急于引入更多概念。

**I. 交接以状态操作为中心——已实测。**

首屏大面积用于“当前生命状态”、两个模拟按钮和未开启的 Executor View；用户没有得到“哪些信息已设置、哪些仍仅本人可见”的总览。

建议保留底部“交接”入口，页面标题改为“交接准备”，先显示授权内容与保持私密的内容，再提供“预览对方能看到什么”。把状态模拟、状态历史放进独立演示页，并始终标注“仅本机模拟”。当前只支持演示执行人，不应画成已经可以邀请亲人或自动发送；真实接收者能力需要后续契约支持。

**J. AI 隐私流程要求用户理解实现术语——源码确认。**

Account、Secret、Money、Note Token 和逐行下拉选择，把脱敏操作变成技术表单；未经标记的文字仍会发送。已有单次授权和外发文本预览应保留。

建议改为“检查将发送的内容”，用中文“账号 / 密码与密钥 / 金额 / 私密备注”，并提供原文与实际发送文本的对照。未配置服务时提供清楚的设置入口，同时保持手工整理可用。任何自动敏感检测只能辅助提示，不能声称自动消除了所有隐私信息。

### P2：降低理解和维护成本

- 术语：Vault → 加密资料库；Secret → 密码/密钥；Executor View → 接收者预览；Provider → AI 服务；“磁盘只保存随机 ID 密文” → “已加密保存在本机”。算法说明保留在安全详情。
- 首次使用：先说明“保存哪些信息、默认谁能看、怎样备份”；推荐口令长度作为默认，高级设置再选词数。生成器会自动填写两次密码，因此当前“再次输入”并未验证记忆。应单独确认用户已妥善保存口令。
- 备份：设置中显示上次成功导出的时间，并解释“保存在本机”与“已有设备外备份”的区别。不能仅凭导出动作就声称外部备份可靠可用。
- 详情：内容优先；来源和确认状态在其后；编辑为主动作；拆分、组合、删除收进更多。历史条目应可展开，避免只显示截断的摘要。
- 视觉：保留暖色和克制圆角，减少大面积深色与重复容器。状态除了颜色，还要有文字。核对“身故”对应的火焰图标是否合适，建议使用中性图形或纯文字。

## 5. 建议的信息架构

保留现有四个主导航，先调整各页职责，降低迁移成本。

| 入口 | 首要问题 | 页面顺序 |
| --- | --- | --- |
| 记录 | 我现在怎样最快留下这件事？ | 快捷记录 → 待整理 → 最近记录 → 全部原件 |
| 卡片 | 我之前记下的内容在哪里？ | 搜索 → 类型/状态筛选 → 内容列表 → 来源与历史 |
| 密码库 | 我如何快速找到并使用一个账号？ | 搜索 → 账号列表 → 复制/按需显示；新增与导入保持可见 |
| 交接 | 某种情况下，对方到底能看到什么？ | 当前授权概览 → 精确预览 → 修改授权 → 独立模拟演示 |
| 设置 | 数据怎样保护、备份和恢复？ | 解锁与锁定 → 备份恢复 → 可选 AI → 技术详情 |

关键路径：解锁 → 先保存一条内容 → 稍后整理 → 确认卡片 → 能回看来源 → 单独设置并预览交接权限。每一步都应有明确的完成状态和回退路径。

## 6. 建议实施顺序与验收

### 第一轮：修复可信度

范围：搜索状态隔离、按钮对比度、授权范围准确表达、恢复入口和回收流程。

验收：搜索无结果不改变首页最近内容；每种授权档位都能核对具体输出；密码预览默认遮挡；被移入回收区的测试卡可恢复；空设备无需先创建临时资料库就能进入备份恢复。

### 第二轮：缩短日常路径

范围：首页层级、轻量编辑、待整理入口、全部原件及来源链接、正确的空状态。部分来源和回收能力需要应用层支持，应拆成独立实现任务。

建议验证：让首次接触者保存“备用钥匙在鞋柜第二层”，无需理解分类术语；让已有几十条资料的用户找到其中一条、打开原件并修改；保留旧版本。可把“解锁后 15 秒内保存一条简短记录”和“30 秒内找到指定资料”作为首轮测试目标，再根据实际观察调整。

### 第三轮：交接准备与视觉收敛

范围：集中授权总览、独立模拟页、技术文案迁移、设计系统和可访问性。

验收任务：用户在不听解释的情况下说清某张卡在临时失能/身故情境下会显示哪些内容；明确知道当前仅本机模拟。建议先做 5–8 人定性测试，以目标年轻用户为主，加入不同数字熟练度的家庭成员观察术语理解；该规模不用于统计推断。

可访问性检查：普通文字对比度至少 4.5:1，大字号至少 3:1，触控目标至少 48×48dp；增加 200% 字体、小屏、深色模式、TalkBack 的任务走查。数值依据 [Android 官方可访问性指南](https://developer.android.com/guide/topics/ui/accessibility/apps.html)，核验于 2026-10-01。200% 字体是本报告建议的测试条件。

## 7. 实现边界

- 表现层可先完成：文案、颜色、层级、状态反馈、已有能力的入口重组。
- 应用层需要配合：独立搜索状态、最近数据、加密草稿保存、全部原件查询、回收恢复、备份状态。
- 需先确认产品/领域设计：自定义交接摘要、字段级授权、真实接收者和真实交接流程。
- 本评估任务当时未修改 Flutter/Android 实现。后续用户已确认方案并要求一次交付，实施事实见交付记录；第 6 节三轮仅作为本次内部顺序，评估内容保留为历史依据。
